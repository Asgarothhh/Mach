# Спецификация: аудит интерфейса и правки против «ИИ-слопа» (apps/web)

**Статус:** черновик для согласования (frontend/UI, продукт, бренд)
**Дата:** 14 октября 2026 г.
**Область:** весь клиентский интерфейс `apps/web` (публичный портал, экраны голоса и текста, админка). Backend, контракты API и тексты юридических уведомлений не меняются.
**Связанные документы:** `apps/web/docs/ui-screen-map.md`, `docs/SPEC_MASCOT_CUBE_UI_CHANGE.md`, концепт `ui-anti-slop-concept.pdf` (первая версия), `interface-anti-slop-audit-concept.pdf` (этот аудит).

> Термин «ИИ-слоп» здесь означает признаки шаблонного, сгенерированного интерфейса: декор без данных, одинаковые карточки с иконками, лозунги вместо конкретных фраз, тире и тройки в тексте, повторяющиеся дисклеймеры. Цель — не «убрать ИИ», а сделать интерфейс конкретным, спокойным и читаемым.

**Главный вывод.** Интерфейс не выглядит «сломанным». Он выглядит как набор шаблонов, которые наложили друг на друга: декоративная главная, карточки-метрики почти на каждом экране, одинаковые eyebrow над каждым заголовком, одни и те же дисклеймеры по всему приложению. Пользователь (оператор или владелец бизнеса) тратит внимание на оформление, а не на данные.

## 3. Принципы правок

1. **Данные вместо декора.** Если элемент не показывает состояние, данные или действие, он убирается. Волна, орбиты, плавающие цифры и декоративные точки — кандидаты на удаление.
2. **Один заголовок на экран.** Eyebrow остаётся только там, где он даёт категорию, которой нет в заголовке. Иначе убирается.
3. **Одно место для каждого предупреждения.** Оговорки о демо, о телефонии и о персональных данных показываются один раз на экран, в месте, где пользователь принимает решение. Футер не дублирует предупреждения шапки и диалога.
4. **Русский продукт — русские подписи.** Англоязычные служебные метки (`NEW DRAFT`, `SCENARIO CONFIG`, `Read-only demo`, `tenant_id`) заменяются русскими формулировками. Технические идентификаторы показываются в раскрывающихся блоках или на уровне разработчика.
5. **Без тире в UI-тексте.** Используются точка, двоеточие или перенос. Тире допускаются только в юридических текстах, которые утверждает владелец.
6. **Конкретные фразы.** Лозунг заменяется фактом о текущем состоянии (см. раздел 6).
7. **Один радиус и одна шкала текста.** Радиусы и размеры шрифта приводятся к токенам (раздел 5).
8. **Плотность для рабочих экранов.** Админка и история звонков — рабочие инструменты: меньше рамок, больше строк на экран, цифры выравниваются вправо.
9. **Не ломать требования безопасности.** Демо-маркировка, разделение тестового канала и телефонии, предупреждения о персональных данных, `can_view_original` и права на правки остаются. Меняется форма подачи и количество повторов, а не сам факт.

## 5. Токены (предложение для `src/styles/tokens.css`)

Значения предварительные. Проверить контраст WCAG AA (4.5:1 для обычного текста) и согласовать с брендбуком.

| Группа | Токен | Значение | Использование |
|---|---|---|---|
| Радиусы | `--radius-field` | 6px | поля, строки таблиц, бейджи |
| | `--radius-control` | 8px | кнопки |
| | `--radius-panel` | 12px | панели и модальные окна |
| Текст | `--text-xs` | 12px | подписи, метки таблиц (минимум) |
| | `--text-sm` | 13px | таблицы, вторичный текст |
| | `--text-md` | 15px | основной текст |
| | `--text-lg` | 18px | подзаголовки |
| | `--text-xl` | 24px | заголовки страниц |
| Поверхности | `--surface` | #ffffff | основной фон |
| | `--surface-muted` | #f6f7f9 | фон сайдбара, шапки таблиц |
| | `--border` | #e3e6ec | все разделители, 1 px |
| Акцент | `--accent` | `--color-brand` (#ed0010) | только основная кнопка и критичные состояния |
| Шрифт | `--font-mono` | ui-monospace, SFMono-Regular | ID, время, коды |

**Правила:**

- Минимальный размер текста — 12 px. Класс `font-size: 9px` и `10px` убирается.
- Радиусы — только из трёх значений выше. Исключение: круглые элементы (`border-radius: 50%`) и пилюли (`999px`).
- Тени только у выпадающих меню и модальных окон. У карточек — только `border`.
- Анимация `translateY` при наведении не используется.

## 6. Правила текста

| Вместо | Пишем |
|---|---|
| «Ни один важный звонок не потеряется.» | «Входящие за сегодня: 12. Передано сотруднику: 3.» (с реальными или помеченными демо-данными) |
| «Честный ответ, если данных нет» | «Если в материалах ответа нет, помощник сообщает об этом и предлагает передать вопрос сотруднику.» |
| «Разговор в браузере — это не телефонный звонок.» | «Тестовый разговор в браузере. Телефонная линия не задействована.» |
| «Здравствуйте, {tenantName}» | «{tenantName}: обзор за сегодня» |
| «Управляйте входящими обращениями, сценарием…» | убрать |
| «NEW DRAFT» | «Новый черновик» |
| «Read-only demo» | «Только просмотр» |
| «В этом макете оценка не отправляется» | «Оценка сохраняется на этой странице до закрытия» |
| «В рабочем режиме это место обновляется событиями streaming ASR» | «Здесь появится текст, когда вы закончите фразу» |

Правила:

1. Тире в UI не используются (кроме юридических текстов, утверждённых владельцем).
2. Одна мысль — одна строка. Не более одного предупреждения на экран в одном месте.
3. Числа и факты — только из данных или с пометкой «демо».
4. Обещания («быстро», «гарантирует», «никогда не потеряется») не используются, пока не подтверждены процессом.
5. Название продукта — одно (см. раздел 7, открытый вопрос 1).

## 7. Открытые вопросы

1. **Название продукта.** Нужно выбрать одно: «ИИ-агент звонков» (бренд в шапке), «Голосовой помощник» (текущая навигация) или «MTS Inbound Voice Agent» (техническое). Выбор влияет на `<title>`, шапку, футер и тексты.
2. **Предупреждения.** Кто утверждает формулировки про персональные данные и телефонию (юристы, владелец продукта). Без утверждения менять их нельзя, только количество повторов.
3. **Метрики на главной.** Какие цифры показывать в реальном режиме и откуда они берутся. Пока их нет, блок в демо помечается как демо.
4. **Таймер подключения.** Нужен ли он бизнесу как продуктовая метрика. Если да — он должен считаться на сервере, а не в браузере.
5. **Цвет и бренд.** Используется ли `--color-brand` как единственный акцент или нужен второй цвет для статусов. Согласовать с бренд-командой.
6. **Админка.** Насколько плотной должна быть таблица звонков (число колонок и высота строки). Зависит от того, кто работает в админке: оператор или владелец.
